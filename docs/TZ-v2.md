## 1. Цель и границы

Кроссплатформенный десктопный мессенджер (Windows 10/11, Linux Ubuntu 22.04+): регистрация/вход, список чатов, обмен текстом и медиа (фото, видео, GIF, файлы), история в SQLite, современный UI с двумя темами.

**Границы:**
- работа в пределах локальной сети или localhost; шифрование канала не требуется (см. §9.2);
- без облачных сервисов, без внешних фреймворков (только Qt + STL);
- шаблон: «клон → 3 команды → работает», без ручной правки путей.

**Персоны/сценарий проверки:** два экземпляра клиента на одной машине + локальный сервер; обмен текстом, фото, видео, GIF; перезапуск клиента → история на месте.

## 2. Технологический стек

| Компонент | Требование |

| UI | Qt Widgets + QSS; QML не используется |
| Сеть | `QTcpSocket` / `QTcpServer`, неблокирующий режим, собственный фрейминг |
| БД | SQLite через Qt SQL (QSQLITE), режим WAL |
| Медиа | `QMediaPlayer` + `QVideoWidget`, `QMovie` (GIF), `QImageReader`/`QPixmap` |
| Модули Qt | Core, Gui, Widgets, Network, Sql, Multimedia, MultimediaWidgets, Concurrent, Svg |
| Сборка | CMake ≥ 3.16, target-based; `CMakePresets.json` |
| Поддержка Qt | **Qt 5.15.x (приоритет), 5.14.2 — проверенная нижняя граница**; Qt 6 — вне объёма v2 |
| Минимальные версии | Qt 5.14 (нужен `QPasswordDigestor`, появился в 5.12) |

Обоснование «только Qt 5»: в Qt 6 полностью переписан `QMediaPlayer` (нет `setMedia(QMediaContent)`, другой backend), и поддержка двух веток превращает ~15 % кода в `#if QT_VERSION`. Если нужна Qt 6 — это отдельное решение, см. вопросы в PROPOSAL.md.

## 3. Архитектура

### 3.1. Компоновка

```
messenger_core (статическая библиотека)
├─ protocol/   фрейминг, JSON-конверт, коды ошибок, лимиты
├─ data/       БД, миграции, репозитории, outbox
├─ security/   PBKDF2, токены, валидация ввода
└─ media/      пробинг медиа, превью, миниатюры

MessengerServer (exe)  ── uses ── messenger_core
MessengerClient (exe)  ── uses ── messenger_core
```

Два исполняемых файла вместо одного с `--server`: чище по зависимостям (клиент не тянет серверный код), проще отладка двух процессов, и это не усложняет сборку. Один `cmake --build` собирает всё.

### 3.2. Слои

| Слой | Ответственность | Запрещено |
|---|---|---|
| `ui/` | виджеты, модели списков, анимации | SQL, сокеты, файловый ввод-вывод |
| `app/` | сервисы-фасады (`ChatService`, `SessionService`), сигналы для UI | знание о виджетах |
| `net/` | соединение, переподключение, кодеки, передача файлов | SQL |
| `data/` | репозитории, транзакции, миграции | сеть, UI |
| `server/` | сессии, роутинг, права, рассылка | UI |

### 3.3. Модель потоков

**Клиент**
- GUI-поток: виджеты, `QTcpSocket` (неблокирующий), кодеки кадров. Сетевые операции не блокируют цикл событий — отдельный поток сокету не нужен.
- Поток БД (`QThread` + worker-объект): единственное соединение `QSqlDatabase` создаётся **внутри** `run()`, имя `client-<threadId>`; все запросы — через queued-сигналы. Соединения Qt SQL не потокобезопасны и не переносимы между потоками.
- Пул миниатюр: `QThreadPool` (макс. 2) для декодирования изображений/видеокадров.
- Правило: сокет и БД никогда не живут в одном потоке с виджетами и не вызываются напрямую из UI.

**Сервер**
- Единственный event-loop поток: `QTcpServer` + асинхронные `QTcpSocket` всех клиентов, один поток БД для записи.
- Отказ от «поток на соединение»: при общей SQLite это даёт `database is locked`, гонки на `seq` и лишнюю сложность. Асинхронный single-thread выдерживает десятки клиентов, а тяжёлые операции (файлы 25 МБ) пишутся потоково, без блокировки цикла событиями.
- SQLite: `journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=5000`, `foreign_keys=ON`.

## 4. Модель данных

### 4.1. Серверная БД (`server.db`)

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);  -- schema_version, created_at

CREATE TABLE users (
  id           INTEGER PRIMARY KEY,
  username     TEXT    NOT NULL COLLATE NOCASE UNIQUE,  -- 3..32, [a-z0-9_.-]
  display_name TEXT    NOT NULL,                        -- 1..48
  pwd_salt     BLOB    NOT NULL,                        -- 16 байт
  pwd_hash     BLOB    NOT NULL,                        -- 32 байта, PBKDF2-HMAC-SHA256
  pwd_iters    INTEGER NOT NULL,
  avatar_hue   INTEGER NOT NULL DEFAULT 210,            -- 0..359, цвет fallback-аватара
  created_at   INTEGER NOT NULL                         -- unix ms, UTC
);

CREATE TABLE sessions (
  token      TEXT PRIMARY KEY,          -- 32 случайных байта hex
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at INTEGER NOT NULL,
  last_seen  INTEGER NOT NULL,
  expires_at INTEGER NOT NULL
);

CREATE TABLE chats (
  id         INTEGER PRIMARY KEY,
  kind       TEXT NOT NULL CHECK (kind IN ('direct','group')),
  title      TEXT,
  created_at INTEGER NOT NULL
);

CREATE TABLE chat_members (
  chat_id       INTEGER NOT NULL REFERENCES chats(id) ON DELETE CASCADE,
  user_id       INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  last_read_seq INTEGER NOT NULL DEFAULT 0,
  joined_at     INTEGER NOT NULL,
  PRIMARY KEY (chat_id, user_id)
);

CREATE TABLE messages (
  id            INTEGER PRIMARY KEY,
  chat_id       INTEGER NOT NULL REFERENCES chats(id) ON DELETE CASCADE,
  sender_id     INTEGER NOT NULL REFERENCES users(id),
  seq           INTEGER NOT NULL,                  -- порядковый номер внутри чата
  client_msg_id TEXT    NOT NULL,                  -- UUID клиента, идемпотентность
  kind          TEXT    NOT NULL CHECK (kind IN ('text','image','video','gif','file')),
  body          TEXT    NOT NULL DEFAULT '',
  created_at    INTEGER NOT NULL,
  UNIQUE (chat_id, seq)
);
CREATE UNIQUE INDEX ux_msg_client ON messages(sender_id, client_msg_id);
CREATE INDEX ix_msg_chat ON messages(chat_id, seq DESC);

CREATE TABLE attachments (
  id          INTEGER PRIMARY KEY,
  message_id  INTEGER NOT NULL UNIQUE REFERENCES messages(id) ON DELETE CASCADE,
  file_name   TEXT NOT NULL,      -- исходное имя (только для показа)
  mime        TEXT NOT NULL,
  byte_size   INTEGER NOT NULL,
  sha256      TEXT NOT NULL,
  rel_path    TEXT NOT NULL,      -- attachments/ab/abcdef... (относительно data/)
  thumb_path  TEXT,
  width       INTEGER, height INTEGER, duration_ms INTEGER
);

CREATE TABLE receipts (
  message_id INTEGER NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  state      TEXT NOT NULL CHECK (state IN ('delivered','read')),
  ts         INTEGER NOT NULL,
  PRIMARY KEY (message_id, user_id, state)
);
```

### 4.2. Клиентская БД (`client.db`)

Те же таблицы `users/chats/chat_members/messages/attachments/receipts`, но:
- `users` без `pwd_*` (пароль клиент не хранит никогда, кроме опции «запомнить» — токен в QSettings);
- дополнительно `outbox` для офлайн-очереди:

```sql
CREATE TABLE outbox (
  client_msg_id TEXT PRIMARY KEY,
  chat_id       INTEGER NOT NULL,
  kind          TEXT    NOT NULL,
  body          TEXT,
  attach_path   TEXT,
  state         TEXT    NOT NULL CHECK (state IN ('pending','sending','failed')),
  attempts      INTEGER NOT NULL DEFAULT 0,
  created_at    INTEGER NOT NULL
);
CREATE INDEX ix_outbox_chat ON outbox(chat_id, created_at);
```

### 4.3. Файловое хранилище

```
<AppDataLocation>/MessengerApp/
├─ client.db
├─ server.db
├─ logs/2026-11-07.log
├─ attachments/ab/ab3f...   ← контент-адресация по sha256
├─ thumbnails/ab/ab3f....jpg
└─ tmp/                     ← незавершённые передачи, чистится на старте
```

- Имя файла на диске = `sha256`, исходное имя — только в БД (защита от path traversal);
- атомарная запись: `tmp/<uuid>.part` → `fsync` → `rename`;
- путь переопределяется переменной `MESSENGER_DATA_DIR` (нужно для тестов и CI);
- миграции: `PRAGMA user_version`, последовательные шаги `1→2→…`, каждый в транзакции; при `user_version` новее кода — отказ с понятным сообщением.

## 5. Протокол

Полная спецификация — [protocol.md](protocol.md). Кратко:

- транспорт TCP, кадр = `uint32 len (BE) | uint8 type | uint8 flags | uint16 rsv | payload`;
- `type=1` — JSON-конверт `{"v":1,"id":…,"type":…,"data":{…}}`;
- `type=2` — бинарный чанк файла (`transfer_id`, `seq`, данные);
- лимиты: JSON-кадр ≤ 1 МиБ, чанк ≤ 256 КиБ, вложение ≤ 25 МиБ, текст ≤ 4000 символов;
- ответ на запрос — `reply_to`, ошибка — `{"ok":false,"error":{"code","message"}}`;
- события сервера — `ev.*` (новое сообщение, прочтение, присутствие, набор текста);
- heartbeat `ping/pong` каждые 30 с, idle-таймаут 120 с, переподключение с экспоненциальной задержкой 1→30 с;
- идемпотентность: повтор `msg.send` с тем же `client_msg_id` возвращает тот же `message_id` (не дубликат).

## 6. Функциональные требования

### F-01. Регистрация и вход
- Экран входа: логин, пароль, «Запомнить меня», ссылка «Создать аккаунт», выбор сервера (host:port), переключатель темы.
- Регистрация: логин, отображаемое имя, пароль, повтор пароля; валидация на клиенте и сервере.
- Пароль: PBKDF2-HMAC-SHA256, соль 16 байт на пользователя, 120 000 итераций, сравнение за постоянное время (`QMessageAuthenticationCode` / побайтовое сравнение с накоплением XOR).
- Ошибки: «неверный логин или пароль» (без указания, что именно), «логин занят», «сервер недоступен».
- Сессия: сервер выдаёт токен (TTL 30 дней), клиент хранит его в `QSettings`; повторный запуск — `auth.resume` без ввода пароля; кнопка «Выйти» удаляет токен.

### F-02. Список чатов
- Слева: шапка профиля (аватар, имя, меню), поиск по чатам, список.
- Элемент: аватар (или инициалы на цвете из `avatar_hue`), имя, последнее сообщение (1 строка с эллипсисом, префикс «Вы:», «📷 Фото» для медиа), время (ЧЧ:ММ / «Вчера» / ДД.ММ), бейдж непрочитанных.
- Сортировка: по времени последнего сообщения, закреплённый «Общий чат» — всегда сверху.
- Пустое состояние: «Пока нет чатов. Начните переписку».
- Создание личного чата: кнопка «+» → поиск пользователя по логину → чат.

### F-03. Окно чата
- Шапка: аватар, имя, статус («в сети» / «был(а) 12:30»), кнопки «поиск в чате», «настройки».
- Лента: пузыри, группировка подряд идущих сообщений одного автора (< 5 мин), разделители дат («Сегодня», «Вчера», «7 ноября»), аватары только у первого сообщения группы.
- Свой пузырь справа, акцентный фон; чужой слева, фон поверхности; максимальная ширина 65 % панели.
- Время в пузыре + статус: `✓` отправлено, `✓✓` доставлено, `✓✓` (акцент) прочитано, `!` ошибка с тултипом и кнопкой «Повторить».
- Прокрутка: автоскролл к низу, если пользователь у нижней границы; иначе плашка «Новые сообщения ↓».
- Пагинация: 50 сообщений, при прокрутке к верху — подгрузка предыдущих с сохранением позиции скролла.
- Поле ввода: многострочное, автовысота 1→6 строк, Enter — отправить, Shift+Enter — перенос, кнопка «скрепка», кнопка отправки (активна при непустом вводе или вложении).
- Индикатор «печатает…» под шапкой (опционально, F-09).

### F-04. Вложения
- `QFileDialog` с фильтром: изображения (png/jpg/jpeg/webp/bmp/gif), видео (mp4/mov/mkv/webm/avi), любой файл.
- Проверки до отправки: размер ≤ 25 МиБ, читаемость, MIME по расширению и сигнатуре.
- Предпросмотр: миниатюра + имя + размер + кнопка отмены до отправки; после отправки — прогресс-бар в пузыре.
- Отображение в ленте:
  - фото — превью ≤ 320×240, скруглённое, клик → лайтбокс (масштаб, Esc, стрелки);
  - GIF — анимируется через `QMovie`, один активный экземпляр на сообщение, пауза при уходе из видимой области;
  - видео — постер (первый кадр) + кнопка ▶, клик → модальный плеер `QMediaPlayer`+`QVideoWidget` (play/pause, перемотка, громкость, время); одновременно играет не более одного ролика;
  - произвольный файл — плитка с иконкой, именем, размером, кнопкой «Сохранить как…».
- Ошибки: «Файл больше 25 МБ», «Не удалось прочитать файл», «Вложение недоступно» (файл потерян) — плитка-заглушка, приложение не падает.
- Передача: чанками по 64 КиБ, возобновление не требуется (повтор с нуля), проверка sha256 на сервере и клиенте.

### F-05. История
- Все сообщения и метаданные — в SQLite; при старте лента восстанавливается из локальной БД мгновенно, затем синхронизируется с сервером.
- Отправленные офлайн сообщения лежат в `outbox` со статусом «часики», отправляются при восстановлении связи в исходном порядке.

### F-06. Сервер
- `MessengerServer --port 45000 --data <dir> --verbose`.
- Первый запуск: создаёт БД, создаёт «Общий чат» (group), привязывает к нему всех новых пользователей.
- Обрабатывает: регистрацию, вход, resume, список чатов, историю, отправку, прочтение, вложения, ping.
- Рассылает: `ev.msg` всем участникам чата, `ev.read`, `ev.presence`, `ev.typing`, `ev.chat`.
- Права: доступ только к чатам, где пользователь — участник (иначе `NOT_MEMBER`).
- Лимиты: 64 соединения, 20 сообщений/мин на пользователя, 2 параллельные передачи на соединение.
- Корректное завершение по SIGINT/консоли: закрыть сокеты, `commit`, закрыть БД.

### F-07. Статусы доставки и прочтения
- `sent` — сервер подтвердил запись (`msg.ack`);
- `delivered` — у получателя открыт сокет и кадр дошёл до его клиента (клиент шлёт `receipt.delivered`);
- `read` — получатель открыл чат / проскроллил до сообщения (`chat.read`), сервер сохраняет `last_read_seq` и рассылает `ev.read`.
- Отправитель видит агрегированный статус по худшему из получателей (для групп).

### F-08. Поиск (P1)
- Глобальный поиск по сообщениям в локальной БД (LIKE, регистронезависимо, ≤ 100 результатов), переход к сообщению с подсветкой.
- Поиск по чатам — фильтрация списка на лету.

### F-09. Присутствие и «печатает» (P1)
- `ev.presence` при подключении/отключении (heartbeat-таймаут 90 с), last_seen.
- `ev.typing` с троттлингом 2 с, автосброс через 5 с.

### F-10. Уведомления (P1)
- `QSystemTrayIcon`: бейдж непрочитанных, всплывающее уведомление при сообщении в неактивном чате, клик — открыть чат.
- Отключаемо в настройках; при активном окне и открытом чате — не показывать.

### F-11. Настройки (P0)
- Тема (светлая/тёмная/системная), размер шрифта (S/M/L), уведомления вкл/выкл, адрес сервера, «Выйти», «Очистить кэш», папка данных (открыть в проводнике).

### F-12. Локализация (P1)
- RU (по умолчанию) + EN, `.ts`/`.qm` через `QTranslator`; все строки — через `tr()`, без хардкода в виджетах.

### 7.3. Анимации
- Появление сообщения: opacity 0→1 + сдвиг 8 px, 160 мс, `OutCubic` (`QPropertyAnimation`), только для новых сообщений (история — без анимации).
- Hover: 120 мс смена фона элементов списка.
- Переключение темы: мгновенно (без вспышки), через `QPalette` + повторную загрузку QSS.
- Учитывать `QStyleHints` / системную настройку анимаций не обязательно, но анимации не должны ломать скролл.

### 7.4. Состояния
- Загрузка истории — скелетоны 3 строки.
- Пустой чат — «Напишите первое сообщение».
- Нет сети — жёлтый баннер сверху «Нет соединения. Переподключение… (5)».
- Ошибка сервера — красный баннер с «Повторить».
- Ошибка авторизации — inline под полем.

### 7.5. Доступность
- Полная навигация с клавиатуры, видимый фокус, `Tab`-порядок, шорткаты: `Ctrl+N` новый чат, `Ctrl+F` поиск, `Esc` закрыть диалог, `Ctrl+Enter` отправить (альтернатива Enter).
- Контраст текста ≥ 4.5:1 в обеих темах.
- Курсор `PointingHandCursor` на кликабельных элементах, тултипы с шорткатами.

## 8. Нефункциональные требования

### 8.1. Производительность
- Старт до показа окна ≤ 1.5 с; открытие чата с 1000 сообщений ≤ 300 мс (виртуализация не требуется, но список наполняется батчами).
- Скролл 60 fps на 5000 сообщениях: пузыри — лёгкие виджеты, без теней и эффектов.
- Декодирование изображений — вне GUI-потока, кэш миниатюр в памяти (LRU, ≤ 64 МБ).

### 8.2. Безопасность
- PBKDF2 (см. F-01); соль уникальна; токены — CSPRNG (`QRandomGenerator::system()`).
- Все SQL-запросы — `prepare` + bind (никакой конкатенации).
- Имена файлов на диске не берутся из пользовательского ввода; проверка что `rel_path` не выходит за пределы `attachments/`.
- Санитизация текста: сообщение — plain text (без HTML), ссылки определяются регуляркой и открываются через `QDesktopServices` только для `http/https`; никакого `setHtml` с пользовательскими данными.
- Лимиты кадров и rate-limit на сервере; логи без паролей/токенов.
- **Вне объёма:** TLS, E2E-шифрование; в README — явное предупреждение «трафик не шифруется, использовать в доверенной сети».

### 8.3. Устойчивость
- Нет сервера при старте → экран входа с понятным сообщением и кнопкой «Повторить».
- Обрыв соединения → авто-реконнект (1, 2, 4, 8, 16, 30 с), очередь outbox сохраняется.
- БД повреждена → `PRAGMA integrity_check`; при ошибке файл переименовывается в `*.corrupt-<ts>`, создаётся новая БД, пользователю показывается диалог с путём бэкапа.
- Нет файла вложения → заглушка «Файл недоступен».
- Нет прав на запись / диск полон → баннер с текстом ошибки, приложение не падает.
- Любое исключение на границе (парсинг JSON, кадр) → лог + закрытие соединения, не крэш.
- Single-instance: `QLockFile` в папке данных; повторный запуск поднимает существующее окно.

### 8.4. Логирование
- `qInstallMessageHandler` → `logs/app-YYYY-MM-DD.log`, ротация 5 файлов × 5 МБ, UTF-8, потокобезопасно (`QMutex`).
- Формат: `2026-11-07 12:00:00.123 [INFO ] [net] сообщение`.
- Уровни: DEBUG (только с `--verbose`), INFO, WARNING, CRITICAL; сообщение о крэше — в лог и `QMessageBox`.
- Запрещено логировать пароли, токены, содержимое сообщений (только id и размеры).

### 8.5. Код
- C++17, без `using namespace` в заголовках, RAII, `nullptr`, `override`.
- Публичные API — с Doxygen-комментариями (русский), приватные — по необходимости.
- Никаких `TODO`/заглушек в поставляемом коде (критерий ТЗ); допустимы `// P2` пометки только в docs.
- clang-format (файл `.clang-format`), сборка без предупреждений на `-Wall -Wextra`.

## 9. Сборка, запуск, упаковка

### 9.1. Команды
```bash
# Windows (MSVC x64, Qt 5.15)
cmake -S . -B build -G "Visual Studio 17 2022" -A x64 -DCMAKE_PREFIX_PATH=C:/Qt/5.15.2/msvc2019_64
cmake --build build --config Release

# Windows (MinGW)
cmake -S . -B build -G "MinGW Makefiles" -DCMAKE_PREFIX_PATH=C:/Qt/5.15.2/mingw73_64
cmake --build build -j

# Linux
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j$(nproc)
```
Запуск: `build/MessengerServer` + два `build/MessengerClient`; либо `scripts/run-demo.ps1` / `run-demo.sh`.

### 9.2. Первый запуск
- Клиент/сервер сами создают `AppDataLocation/MessengerApp/{logs,attachments,thumbnails,tmp}`.
- Адрес сервера по умолчанию `127.0.0.1:45000`, меняется в настройках и через `MESSENGER_SERVER`.
- Ошибок «нет файла конфигурации» быть не должно.

### 9.3. Пакетирование (P1)
- `windeployqt` в `cmake --install` + `scripts/package-windows.ps1` (папка `dist/` запускается без Qt в PATH).
- Linux: `cmake --install` + описанные зависимости (`qtmultimedia5-dev`, `gstreamer1.0-plugins-good/bad`).
- GitHub Actions: Windows (MSVC + Qt aqtinstall), Ubuntu 22.04 (apt qtbase5-dev qtmultimedia5-dev) — сборка + ctest.

## 10. Тестирование

| Набор | Что проверяет |
|---|---|
| `tst_protocol` | фрейминг (частичные кадры, склейка, мусор, превышение лимита), JSON-конверт, коды ошибок |
| `tst_password` | PBKDF2: детерминизм, уникальность соли, неверный пароль, константное время (косвенно) |
| `tst_db` | миграции 1→N, идемпотентность `client_msg_id`, пагинация по seq, каскадное удаление, восстановление после повреждения |
| `tst_server_smoke` | headless-сервер: регистрация → вход → 2 клиента → текст → ack → read; вложение 1 МБ end-to-end |
| `tst_media` | определение типа по сигнатуре, генерация миниатюр, отказ на битом файле |

- CTest, тесты не требуют дисплея (`QT_QPA_PLATFORM=offscreen`), данные — во временной папке.
- Ручной чек-лист приёмки — в README (два клиента, медиа, рестарт).

## 11. Критерии готовности (DoD)

1. `git clone` + 2–3 команды → собирается на Windows (MSVC и MinGW) и Ubuntu 22.04 без правок.
2. Регистрация, вход, «запомнить», выход работают; неверный пароль — понятная ошибка.
3. Два клиента обмениваются текстом в реальном времени; история сохраняется после перезапуска обоих.
4. Фото, GIF, видео и произвольный файл отправляются и отображаются; 26 МБ — отклоняется с сообщением.
5. Статусы sent/delivered/read и счётчики непрочитанных корректны.
6. Обе темы, переключение на лету, fallback-аватары, анимация появления сообщений.
7. Обрыв/восстановление сети: реконнект без потери введённого и без дублей.
8. Повреждённая БД и отсутствующий файл не роняют приложение.
9. `ctest` — 100 % зелёные; сборка без предупреждений.
10. README: скриншоты, команды, зависимости, порядок запуска; нет `TODO` в коде.

## 12. Вне объёма v2

- TLS/шифрование, E2E, серверные push-уведомления;
- групповые чаты с управлением участниками (только «Общий чат» + личные);
- редактирование/удаление сообщений, реакции, ответы (цитирование);
- звонки, голосовые сообщения, стикеры, кастомные эмодзи-паки;
- синхронизация между устройствами, веб/мобильные клиенты;
- Qt 6 (при отдельном решении — см. PROPOSAL.md);
- федерация серверов, модерация, роли.
