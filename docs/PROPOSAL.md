## 2. Правки ТЗ: что не так и что предлагаю

### Критичные (ломают работоспособность или противоречат сами себе)

**П-1. Вложения не доедут до получателя.**
ТЗ: «вложения хранятся в локальной папке `attachments/`, в БД только путь». При клиент-серверной модели получатель видит путь к файлу на чужой машине. Это не деталь реализации, а дефект архитектуры.
→ Файл идёт через сервер: клиент загружает чанками, сервер хранит контент-адресованно (`sha256`), получатель скачивает в свой кэш. В БД — метаданные + относительный путь. (TZ-v2 §4.3, protocol §6–7.)

**П-2. Пароли: SHA-256 с солью — недостаточно.**
Одна итерация SHA-256 перебирается на GPU миллиардами в секунду. Salt защищает от радужных таблиц, но не от брутфорса.
→ PBKDF2-HMAC-SHA256, 120 000 итераций, соль 16 байт, сравнение за постоянное время. Реализуется штатным `QPasswordDigestor` (Qt ≥ 5.12), без внешних зависимостей. (TZ-v2 F-01.)

**П-3. Протокол не задан вообще.**
В ТЗ нет ни формата кадров, ни списка сообщений, ни версионирования. Это самый большой объём неопределённости: без него нельзя ни оценить, ни написать сервер.
→ Бинарный фрейминг (8-байтовый заголовок) + JSON-конверт + бинарные чанки для файлов + явная таблица запросов/событий/кодов ошибок. (protocol.md.)

**П-4. «Сеть и БД вне GUI-потока» — ловушка.**
`QSqlDatabase` нельзя использовать из другого потока и нельзя переносить между потоками; соединение создаётся внутри потока-владельца. `QTcpSocket` в Qt асинхронен и в отдельном потоке не нуждается — перенос сокета в поток только добавляет гонки.
→ Явная модель: GUI-поток владеет сокетом (неблокирующие сигналы), отдельный поток БД с собственным соединением, пул миниатюр. На сервере — один event-loop и один поток БД, без «потока на соединение» (иначе `database is locked` и гонки на `seq`). (TZ-v2 §3.3.)

**П-5. «Статус доставки» без семантики.**
Непонятно, что считается доставкой: запись в БД сервера, получение сокетом или прочтение.
→ Три состояния: отправлено (ack сервера), доставлено (клиент получателя подтвердил кадр), прочитано (`last_read_seq` + `ev.read`). (TZ-v2 F-07.)

**П-6. История «с подгрузкой» без API.**
→ Keyset-пагинация по `seq` (стабильна при новых сообщениях, в отличие от OFFSET), `before_seq` + `has_more`. (protocol §4 `chat.open`.)

### Важные

**П-7. Один бинарник или два — решение не принято.** От этого зависит структура CMake и то, что попадёт в поставку. Предлагаю статическую библиотеку `messenger_core` + два exe. (TZ-v2 §3.1.)

**П-8. Лимит 25 МБ × base64.** Если гнать файл в JSON/base64, 25 МБ превращаются в 33 МБ строки плюс копии — риск OOM и фризов. Отсюда чанки по 64 КиБ и жёсткий лимит кадра.
→ Лимиты вынесены в таблицу (TZ-v2 §13.1), проверяются на клиенте **и** на сервере.

**П-9. «Повреждённая БД — понятное сообщение» без стратегии.**
→ `integrity_check` при старте, карантин файла, автопересоздание, бэкап, диалог с путём. (TZ-v2 §8.3.)

**П-10. Схема БД в ТЗ отсутствует**, хотя требуется в результатах (п. 7.4).
→ Полный DDL с индексами, WAL, миграциями по `user_version`, отдельная клиентская БД + `outbox` для офлайна. (TZ-v2 §4.)

**П-11. C++11 в CMakeLists против C++17 в ТЗ.** Плюс `find_package(Qt5 COMPONENTS Widgets)` без Network/Sql/Multimedia и `cmake_minimum_required(3.5)`. Текущий файл переписывается целиком.

**П-12. Сборка «сразу после клонирования» не обеспечена:** нет `CMakePresets.json`, нет инструкции по `CMAKE_PREFIX_PATH`, нет скриптов запуска, нет проверки на чистой машине (CI).
→ Presets + `scripts/` + GitHub Actions (Windows MSVC, Ubuntu 22.04).

**П-13. Безопасность не описана:** path traversal в именах файлов, HTML-инъекции в тексте сообщений, отсутствие rate-limit, кадры произвольного размера (DoS), логи с паролями.
→ Раздел §8.2 и валидация на границе.

**П-14. Тестов нет.** Для ТЗ с критерием «код компилируемый, без заглушек» тесты — дешёвая страховка: протокол, PBKDF2, миграции, smoke-тест сервера headless. (TZ-v2 §10.)

### Мелкие, но заметные

- **П-15.** `QMovie` для GIF нужно останавливать вне видимой области — иначе 20 гифок в ленте съедают CPU.
- **П-16.** Видео: одновременно должен играть один ролик, клик открывает модальный плеер. Inline-воспроизведение нескольких `QVideoWidget` нестабильно (особенно DirectShow).
- **П-17.** Тени через `QGraphicsDropShadowEffect` дороги при скролле → тени только на карточках, пузыри — фон/рамка.
- **П-18.** HiDPI: `AA_EnableHighDpiScaling` до создания `QApplication`, `AA_UseHighDpiPixmaps`; иконки — SVG.
- **П-19.** Single-instance (`QLockFile`), иначе два клиента пишут в одну БД.
- **П-20.** Время в БД — UTC (`unix ms`), форматирование — локальное; иначе «вчера» ломается при смене пояса.
- **П-21.** Идемпотентность отправки (`client_msg_id`) — без неё реконнект даёт дубли.
- **П-22.** Локализация: строки через `tr()` сразу, иначе потом править 50 файлов.

## 3. Что предлагаю добавить в объём (и что оставить за бортом)

Предлагаю **базовый набор P0 + рекомендованный P1**:

| P0 (обязательно) | P1 (рекомендую) | P2 / вне объёма |
|---|---|---|
| регистрация, вход, resume-сессия | присутствие «в сети / был(а)» | групповые чаты с управлением |
| общий чат + личные | «печатает…» | редактирование/удаление, реакции, ответы |
| текст, фото, GIF, видео, файлы | системный трей + уведомления | голосовые, звонки, стикеры |
| история, пагинация, outbox | поиск по сообщениям | TLS/E2E |
| статусы sent/delivered/read | RU/EN локализация | синхронизация устройств |
| две темы, анимации, fallback-аватары | `windeployqt`-пакет, CI | Qt 6 |
| настройки, логи, восстановление БД | скелетоны, пустые состояния | федерация |

## 6. Риски

| Риск | Вероятность | Смягчение |
|---|---|---|
| Qt 5.14.2 старая: API-расхождения с 5.15/6 | средняя | придерживаться API 5.14, CMake требует ≥ 5.14 |
| Видео на Windows зависит от системных кодеков | высокая | fallback «открыть внешним плеером», тест на H.264 MP4 |
| Linux без GStreamer-плагинов | высокая | явные зависимости в README + проверка при старте |
| Гонки в БД на сервере | средняя | один поток БД, WAL, транзакция на `seq` |
| 25 МБ вложения: память/фризы | средняя | чанки 64 КиБ, запись потоком, без base64 |
| Поток-БД и `QSqlDatabase` misuse | средняя | соединение создаётся в потоке-владельце, имя с threadId, тест на многопоток |
| Объём работ больше ожидаемого | высокая | этапы с приёмкой, M0–M4 как MVP |

## 7. Вопросы, которые нужно закрыть до старта

**Статус на 2026-11-07: закрыто.** В-1 — только Qt 5.14+; В-2 — ядро-библиотека + `MessengerClient`/`MessengerServer`; В-3 — P0 + P1; П-1…П-6 приняты все шесть. Остальные пункты (В-5…В-9) принимаются по рекомендациям из таблицы ниже.

| # | Вопрос | Рекомендую |
|---|---|---|
| В-1 | Ветка Qt: только 5.15/5.14 или поддержка Qt 6 тоже? | **только Qt 5** (Qt 6 = переписанный медиа-слой, +15 % кода в `#if`) |
