# Голосовые каналы и подписка: план

Документ отвечает на два вопроса: можно ли превратить проект в «Discord для голоса»
и как сделать платную кастомизацию. Код пока не реализован — это оценка и план.

> **Статус (1.7.0):** голос работает через **UDP-релей** (Opus, токен комнаты,
> keepalive, джиттер-буфер) и есть **вызовы** (invite/accept/decline/cancel).
> Осталось: индикатор «говорит», push-to-talk, адаптивный буфер, миксер для
> больших групп.

## Часть 1. Голосовые каналы

### Что есть сейчас

Транспорт — TCP с JSON-кадрами. Он хорош для сообщений и файлов, но для голоса
не подходит: при потере пакета TCP ждёт переотправку, и звук «заикается».
Голос требует UDP, своего буфера и кодеков.

### Два пути

| Путь | Плюсы | Минусы |
|---|---|---|
| **A. UDP-релей через наш сервер** | работает за NAT, не нужен WebRTC, влезает в Qt 5.14 + MinGW | больше задержка (через сервер), свой протокол |
| **B. WebRTC (P2P/SFU)** | лучшая задержка, эхоподавление «из коробки», экран/видео | libwebrtc тяжёл для MinGW, ICE/STUN/TURN, DTLS-SRTP — месяцы работы |

Для первого этапа рекомендую **путь A**: голосовой канал как «комната» на нашем
сервере, звук идёт UDP-пакетами через него.

### Архитектура MVP (1:1 и небольшие комнаты)

1. **Сигнализация (TCP, уже есть):**
   - `voice.join {chat_id}` → сервер выдаёт `session_id`, UDP-порт и ключ;
   - `voice.leave`, `voice.mute`, `voice.speaking`;
   - события `voice.peer_joined`, `voice.peer_left`, `voice.speaking`.
2. **Захват звука:** `QAudioInput` (QtMultimedia), PCM 16 бит, 48 кГц, моно,
   кадры по 20 мс (960 сэмплов).
3. **Кодек:** **Opus** (libopus, лицензия BSD), битрейт 32–64 кбит/с, FEC и PLC
   для потерь. Пакет = 20 мс звука.
4. **Транспорт:** `QUdpSocket`. Заголовок пакета: версия, `session_id`, `user_id`,
   `seq`, `timestamp`. Сервер пересылает пакет остальным участникам комнаты
   (для группы — опционально миксер: декодировать, сложить, закодировать каждому).
5. **Буфер:** джиттер-буфер 60–120 мс, переупорядочивание, отбрасывание опоздавших.
6. **Воспроизведение:** `QAudioOutput`, тот же формат.
7. **NAT:** все клиенты сами шлют UDP на публичный адрес сервера — входящие
   соединения не нужны. На сервере открыть UDP-порт (например, 45001).
8. **Шифрование:** ключ комнаты выдаётся по TLS; пакеты шифруются
   XChaCha20-Poly1305 (libsodium) или AES-GCM. Без этого голос будет открытым.

### Задержка

20 мс захват + ~5 мс Opus + сеть + 60–120 мс буфер + 20 мс вывод ≈ **120–200 мс** —
это нормально для разговора, но хуже Discord (там 40–80 мс за счёт P2P/SFU).

### Этапы

| Этап | Содержание | Оценка |
|---|---|---|
| 1 | Локальный loopback: захват → Opus → файл → воспроизведение | 2–3 дня |
| 2 | 1:1 через UDP-релей, push-to-talk, mute | 1–2 недели |
| 3 | Комната 3–8 человек, миксер, индикатор «говорит» | 3–4 недели |
| 4 | Эхоподавление (SpeexDSP), шумоподавление, автоуровень | 1–2 недели |
| 5 | Экран/видео | отдельный проект (месяцы) |

### Что понадобится добавить

- Зависимости: `libopus`, `libsodium` (или OpenSSL для AES-GCM), `speexdsp` (позже).
- Сборка: CMake находит библиотеки; для Windows — `vcpkg` или готовые DLL.
- Сервер: комнаты в памяти, UDP-сокет, ограничение битрейта на пользователя.
- Клиент: устройства ввода/вывода (QAudioDeviceInfo), выбор микрофона в настройках.
- Нагрузка: 1 голосовой поток ~64 кбит/с на направление; 8 человек в комнате
  через релей — ~4 Мбит/с на сервер.

### Вывод

Да, переоборудовать можно: голос — это отдельный UDP-транспорт и кодек, а не
переделка мессенджера. При этом текст, история, вложения и TLS остаются как есть.
Начинать стоит с этапа 1–2 (1:1, push-to-talk) и только потом делать комнаты.

## Часть 2. Кастомизация по подписке

### Модель

- `plans`: `free`, `plus`, `pro` (названия и цены — на ваш выбор).
- `subscriptions`: `user_id`, `plan_id`, `expires_at`, `source` (payment/promo).
- `entitlements`: что именно даёт план — темы, стикеры, бейджи, лимит файлов,
  кастомные эмодзи. Сервер отдаёт их клиенту при входе, клиент применяет.
- Проверка на сервере: запросы вроде `theme.get` возвращают пакет только при
  активной подписке (нельзя обойти правкой клиента).

### Что продавать

1. **Темы** (пакеты QSS-токенов) — самый простой старт: JSON с цветами и
   радиусов, клиент применяет вместо встроенной темы.
2. **Стикеры/эмодзи-паки** — картинки + манифест, кэш на клиенте.
3. **Бейджи профиля** — отображаются в чате и списке.
4. **Больший лимит вложений** (например, 100 МБ вместо 25 МБ).
5. Позже — кастомные звуки уведомлений, «премиум»-аватары.

### Оплата (РФ и не только)

- **YooKassa** или **CloudPayments** — карты РФ, СБП, чеки по 54-ФЗ, вебхуки.
- **Stripe** — для международных платежей, но нужен юридический адрес вне РФ.
- Схема: клиент → сервер `billing.create_payment` → ссылка на оплату →
  вебхук провайдера → сервер продлевает `subscriptions` → клиент получает
  entitlements.
- Обязательно: идемпотентность вебхуков, возвраты, пробный период, оферта и
  политика обработки персональных данных.

### MVP без эквайринга

1. Промокоды: `billing.redeem {code}` → активирует план на N дней.
2. Админ-скрипт на сервере выдаёт подписку вручную.
3. Когда модель устоится — подключить YooKassa.

### Этапы

| Этап | Содержание | Оценка |
|---|---|---|
| 1 | Таблицы plans/subscriptions/entitlements, выдача при входе | 3–5 дней |
| 2 | Пакеты тем: формат, загрузка, применение, проверка подписки | 1 неделя |
| 3 | Промокоды и ручная выдача | 2–3 дня |
| 4 | YooKassa: создание платежа, вебхук, чеки, возвраты | 1–2 недели |
| 5 | Стикеры, бейджи, лимиты | по мере спроса |

### Риски

- Юридические: оферта, налоги, чеки, персональные данные.
- Мобильные сторы потребуют встроенных покупок (IAP), если появится мобильный клиент.
- Пиратство тем: проверка на сервере + подпись пакетов снижают, но не исключают.

### Вывод

Подписка реализуема без переделки архитектуры: это новые таблицы, несколько
запросов и проверка прав. Начать стоит с промокодов и пакетов тем — они дают
проверить спрос до подключения платежей.
