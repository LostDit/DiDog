# Архитектура

## 1. Слои

```
┌──────────────────────────────────────────────────────────────┐
│  ui/          виджеты, модели списков, анимации              │  Qt Widgets
├──────────────────────────────────────────────────────────────┤
│  app/         сервисы-фасады: сессия, чаты, настройки, темы  │  QObject
├──────────────────────────────────────────────────────────────┤
│  net/         соединение, запросы, реконнект, передачи       │  QTcpSocket
│  server/      сессии, роутинг, права, рассылка (только exe)  │  QTcpServer
├──────────────────────────────────────────────────────────────┤
│  core/        протокол, фрейминг, лимиты, ошибки, id         │  QtCore
├──────────────────────────────────────────────────────────────┤
│  data/        SQLite: миграции, репозитории, outbox           │  QtSql
│  security/    PBKDF2, токены, валидация, санитизация текста  │  QtCore
│  media/       тип файла, миниатюры, кэш                       │  QtGui
└──────────────────────────────────────────────────────────────┘
```

Правила зависимостей (проверяются ревью, нарушение — дефект):

- `ui` → `app`, `core` (типы), `data` (только модели данных, не репозитории);
- `app` → `net`, `data`, `security`, `media`; никогда не знает о `ui`;
- `net` → `core`; не знает о `data` (ни одного SQL-запроса);
- `data` → `core`; не знает о сети и UI;
- `core` не зависит ни от чего, кроме QtCore.

## 2. Целевые платформы и процессы

Два исполняемых файла, общая статическая библиотека `messenger_core`:

| Процесс | Что делает | Потоки |
|---|---|---|
| `MessengerServer` | слушает TCP, хранит БД и вложения, рассылает события | 1 event-loop + 1 поток БД |
| `MessengerClient` | UI, локальный кэш, сеть, медиа | GUI-поток + 1 поток БД + пул миниатюр (2) |

## 3. Модель потоков

### Клиент

- **GUI-поток** владеет `QTcpSocket`. Сокет асинхронен: `readyRead`/`disconnected` приходят в цикл
  событий, блокировок нет. Переносить сокет в отдельный поток не нужно и вредно (лишняя
  сериализация и гонки с UI-моделями).
- **Поток БД** (`QThread` + worker-объект `DatabaseWorker`): `QSqlDatabase` создаётся **внутри** `run()`,
  имя соединения содержит id потока. Все обращения — через queued-сигналы/слоты. Ни один
  `QSqlQuery` не создаётся в GUI-потоке.
- **Пул миниатюр** (`QThreadPool`, максимум 2): декодирование изображений, извлечение кадра видео,
  запись миниатюр на диск. Результат возвращается в GUI-поток сигналом.

Причина: `QSqlDatabase` не потокобезопасен и не переносим между потоками; декодирование 25-мегабайтных
JPEG в GUI-потоке даёт фриз на сотни миллисекунд.

### Сервер

Один event-loop поток: `QTcpServer` и все `QTcpSocket` живут в нём, операции неблокирующие.
Запись в БД — через отдельный поток-владелец соединения. Схема «поток на соединение» отклонена:
при общей SQLite она даёт `database is locked`, гонки при выдаче `seq` и заметно больше кода.

SQLite настроен на `journal_mode=WAL`, `busy_timeout=5000`, `foreign_keys=ON`.

## 4. Поток данных: отправка сообщения

```
MessageBubble/Composer
   → ChatService::sendText(chatId, text)
       → MessageRepository::insertLocal(outbox, state=pending)      [поток БД]
       → ClientConnection::request("msg.send", {...})               [GUI-поток]
           → FrameCodec::writeFrame(JSON)                           [сокет]
   ← msg.ack {message_id, seq, created_at}
       → MessageRepository::confirmSent(client_msg_id, ...)         [поток БД]
       → MessageListModel::updateStatus(sent)                       [GUI-поток]
```

Если сокет не подключён, шаг `request` пропускается: запись остаётся в `outbox` со статусом
`pending` и уходит после `connected`. Повтор использует тот же `client_msg_id` — сервер вернёт тот же
`message_id`, дубль не создаётся.

## 5. Поток данных: вложение

```
Composer: выбор файла → проверка размера/типа → превью
   → AttachmentSender::start(): attach.begin {size, sha256, mime}
   → чанки 64 КиБ (type=2) → attach.finish → {attachment_id}
   → msg.send {kind, attachment_id} → ack
Получатель:
   ev.msg → AttachmentTile (заглушка/прогресс)
   → AttachmentReceiver::fetch(): attach.get → чанки → sha256-проверка → atomic rename
   → MediaCache::thumbnail() (пул) → обновление плитки
```

Файл на диске адресуется `sha256`: `attachments/<ab>/<abcdef…>`. Исходное имя хранится только в БД и
используется при «Сохранить как…»; путь никогда не строится из пользовательской строки.

## 6. Схема БД и миграции

- `PRAGMA user_version` — номер схемы. При старте применяются шаги `n → n+1` в транзакции.
- Если версия БД новее кода — приложение отказывается стартовать с понятным сообщением (защита от
  порчи данных старым бинарником).
- При `integrity_check != ok` файл переименовывается в `*.corrupt-<timestamp>`, создаётся новая БД,
  пользователь получает диалог с путём карантина.

## 7. Ошибки и деградация

| Источник | Поведение |
|---|---|
| Сеть недоступна | баннер «Нет соединения», реконнект 1→30 с, outbox сохраняется |
| Сервер закрыл соединение | повтор запроса после реконнекта (idempotent по `client_msg_id`) |
| Таймаут запроса (30 с) | карточка помечается «ошибка», кнопка «Повторить» |
| БД повреждена | карантин + пересоздание (см. §6) |
| Файл вложения отсутствует | плитка-заглушка «Файл недоступен», приложение работает |
| Видео не декодируется | сообщение «Формат не поддерживается», кнопка «Открыть внешним плеером» |
| Диск полон | баннер с текстом ошибки, запись отменяется |

## 8. Точки расширения

- Новый тип сообщения: значение в `core::MessageKind` + ветка в `AttachmentTile`/`MessageBubble`.
- Новая тема: файл `resources/qss/<name>.qss` + набор токенов в `ThemeManager`.
- Новый запрос: запись в `Protocol` (тип + схема), обработчик в `ServerCore::dispatch`, метод в `ChatService`.
